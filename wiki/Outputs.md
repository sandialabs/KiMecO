# 7) Outputs

KiMecO writes both text outputs and SQLite databases.

## 7.1 Text output files

| File | Location | Content |
|---|---|---|
| KiMecO.log | Run launch directory (where `kmo input.json` is started) | Main run log. Contains progress messages, validation and initialization status, timing information, warnings, and errors (errors now include the full Python traceback). Existing log files are rotated with a date suffix when a new run starts with the same log filename. |
| score_info.txt | `KMO_Project/` (or your configured `project_name`) | Per-generation score summary for GOAT tracking. First line is a header (`ITER`, `BEST SCORE`, `GOAT AVERAGE`), followed by one row per generation with the best score and mean GOAT score. |
| goats.txt | `KMO_Project/` | GOAT membership history by generation. Each line corresponds to one generation and stores model tokens as `gen_id_model_id` pairs (for example `3_42`), representing the selected best models used as the GOAT ensemble for that generation. |
| GA_rates.out | `KMO_Project/` | Rate-statistics report written at GA convergence. Contains the selected model count after `max_score` filtering, then pressure/temperature-resolved tables of reaction rates (organized by PES), with geometric-mean and geometric-standard-deviation summaries across eligible models. |
| `{name}P{slot:02d}.out` | Per-job work directory | Final MESS rate-coefficient output for a PES slot. |
| `{name}P{slot:02d}.stderr` | Per-job work directory | MESS stderr of the automech driver (`use_automech=true`), both passes appended; MESS warnings such as "reference energy" are normal. Deleted with the other job files when the job is picked up, kept when it fails. |
| `{name}P{slot:02d}.out.failed` | Per-job work directory | Output of a MESS pass that failed (non-zero exit, no output, or no `Temperature-Pressure Rate Tables:` section), moved here by the automech driver, which prints the reason to stdout and to the `.stderr` file and exits with code 1 (the Slurm task fails). Kept for diagnosis, never read as rates; the pass-1 copy `_{name}P{slot:02d}.out` is kept next to it when pass 2 failed. |
| `_{name}P{slot:02d}.out` | Per-job work directory | Transient MESS pass-1 output, written only when `use_automech=true`. The pass-1 result is always moved here first, but it only survives when well merging was detected: in that case it is the first-pass result kept before the automatic WellExtension well-lumping produces the extended pass-2 input whose result becomes `{name}P{slot:02d}.out`. When no well merging is detected, pass 2 is skipped and this file is moved back to `{name}P{slot:02d}.out` (final rates without `WellExtension`; see the array log below for the warning on a PES whose input has it). With `prompt_reactions=true` pass 2 always runs, so this file always survives, next to the pass-2 `_ped.out` and `_ke.out` files (`{name}P{slot:02d}_ped.out`, `{name}P{slot:02d}_ke.out`, written when the MESS input asks for the PED and microcanonical-rate outputs); the driver deletes none of them on success (in prompt mode KiMecO deletes the `_ped.out` and `_ke.out` files itself once the model has been collected, see the prompt files below). |
| `prompt_{name}.json` | Per-job work directory | Prompt-rates file of a model (`{name}` is the model's kin name, e.g. `G0001E0007`), written only with `prompt_reactions=true`, by the collector job, in one go and only on success. JSON with the pressures and temperatures of the (P, T) grid (exact values; pressure in bar, temperature in K) and one record per prompt channel (PED PES, hot PES, reactant, product, hot species, thermalised-channel flag) with its rate coefficient k = BF * k1 over the grid, in the units of the KIN rows (s-1 unimolecular, cm3 molecule-1 s-1 bimolecular). The channel set is fixed (see `prompt_bf_threshold`). It is not deleted by the cleanup and is required to restart a prompt-mode run. Its rates are also stored in the KIN database as `__prompt` rows (see the KIN_DB entry in the databases section). |
| `prompt_{name}.py`, `prompt_{name}.slurm` | Per-job work directory | Collector script and its Slurm submission file (prompt mode only). The collector is submitted after the PES array with `--dependency=afterok:<array id> --kill-on-invalid-dep=yes`: it runs only if every PES job exited with code 0. Both files are deleted once the model has been collected successfully, and kept on failure. |
| `logs/{name}_{a}.stdout`, `logs/{name}_{a}.err` | `logs/` next to the job | Logs of array task `{a}` of a model (`{name}` is the model's kin name). With `use_automech=true`, the driver prints on stdout a warning when a non-prompt PES whose input declares `WellExtension` had no well vanish in pass 1: pass 2 did not run and the final rates are without `WellExtension`. The warning is on stdout because a non-empty `.err` fails the task; it appears only in these per-task logs. |
| `logs/prompt_{name}.stdout`, `logs/prompt_{name}.err` | `logs/` next to the job | Logs of the collector (prompt mode only). A failure prints `PROMPT COLLECTOR FAILED (model <id>, <name>): <reason>` in the `.err`. Never deleted. |


### Prompt-mode files and failures (`prompt_reactions=true`)

- **Cleanup.** In prompt mode the `.log`, `.inp`, `.aux` and submission files of a model are deleted only after its collector ended and the prompt-rates file was checked; on success the `{name}P{slot:02d}_ped.out`, `{name}P{slot:02d}_ke.out`, collector script and collector submission file go too, the prompt-rates file and `logs/` stay. When a model fails, every file is kept for diagnosis.
- **Stop on failure.** Any collector failure (missing or empty input file, missing fragment DOS, NaN rate or branching fraction, mechanalyzer exiting, no valid prompt-rates file 60 s after the collector left the queue, collector `sbatch` failed, or a PES job that failed so Slurm cancelled the collector) stops `kmo` (and `kmopp`) with an error naming the model; the model is not reset and there is no fallback to thermal rates. KiMecO does not `scancel` anything: other jobs of the run may still be in the queue, so check `squeue` before a restart.
- **Optimizers.** In a prompt-mode optimizer run, one model that cannot be collected (for example a non-converging MESS run) stops the whole run, including the Nelder-Mead swarm: the instances not started are cancelled and the running ones stop at their next evaluation.
- **Restart.** A model counts as finished on restart only if its prompt-rates file exists and all its (P, T) cells hold both their thermal rows and their `__prompt` rows in KIN_DB; otherwise it is resubmitted.
- **Known limitations (not fixed).** (1) A simulation task that crashes is not detected: the job is marked picked up and resubmitted again and again (`_pickup_sim`), so check `squeue` and the simulation logs; a future fix must not read the always-present Cantera 3.2 `clone` DeprecationWarning in the simulation `.err` as a failure. (2) The SIM template calls `ct.ConstPressureMoleReactor(phase=gas, ...)` (Cantera 3.2; `contents=` fails), but the package still pins `cantera>=3.0.0`; Cantera 3.2 warns that `clone` will default to true after 3.2, and the templates read `gas.X` after the reactor advanced, so a later Cantera would record the initial composition unless `clone=False`. (3) The kin job template `kin_arr_tpl.py` (non-automech path) does not redirect MESS stderr like the automech driver. (4) Changing the (P, T) grid when restarting a run is not checked: use a new `project_name`.
- **Temperature grid.** MESS writes integer temperatures, so the collector reads the branching fractions at `floor(T + 0.5)`. A grid temperature exactly at .5 K (for example 298.5) may make the collector stop with a temperature-set mismatch.

## 7.2 Databases (run state and results)

Three SQLite databases are created in `KMO_Project/` and together contain the accumulated data necessary for restart and analysis. The databases contain one table per generation/iteration with names such as `G0001` for the first generation of a GA, `NM0001` for the first Nelder-Mead simplex and `NMS0001` for the first Nelder-Mead Swarm simplexes.

| Database | File name | Content |
|---|---|---|
| SOP_DB | `KMO_DB_SOP.db` | Contains the set of parameters (SOPs) for all models. Each row corresponds to one model and stores the full SOP parameter vector used to build kinetics/simulations. The columns are dynamically built depending on the system's parameters. Also contains SOP metadata (`__sop_item_pes_ids`) that maps SOP items to PES IDs to enforce restart consistency. |
| KIN_DB | `KMO_DB_KIN.db` | Contain the rate coefficients. Rows store pressure (`P`), temperature (`T`), model kinetics id (`kin_id`) , `pes_id`, `from_name`, `to_name`, and rate coefficient `k`. Tables are organized per generation/iterations as described above. With `prompt_reactions=true`, each model also has one extra row per prompt channel and (P, T) point: `pes_id` is the abstraction (PED) PES, `from_name` the reactant of the PED pair, and `to_name` the product fragments joined with `+` followed by the suffix `__prompt` (e.g. `CH2CHCHCH3+H2__prompt`); `k` is in the units of the other rows, and channels with k = 0 are stored too. Row ids of an optimisation run start at 5e11 (thermal rows below, postprocessing rows from 1e12). The simulations use them: the Cantera mechanism gets one irreversible reaction per distinct equation of the prompt channels (channels with the same reactants and products are summed, 3-product channels included), replacing the forward thermal abstraction of each linked pair of PESs, while the MESS reverse is kept (detailed balance does not hold); a prompt row missing at a (P, T) cell stops the run. They are listed in the raw table of the Databases tab of `kmoui`, not in its KIN tab nor in `GA_rates.out`.|
| SIM_DB | `KMO_DB_SIM.db` | Simulation outputs for each model and experiment pair. Rows are keyed by (`mdl_id`, `experiment_id`) and store a binary `result` blob (Feather-encoded profile data). Currently, the content of the decoded result includes time and species profiles used for scoring and postprocessing. However, in the future, it will depend on the specific experimental data provided for the scoring. |

> **Postprocessing writes into these same databases.** Extrapolation no longer creates separate `PP_DB_KIN.db` / `PP_DB_SIM.db` files. Extrapolated rate coefficients are appended into the existing KIN tables for the originating generation (reusing any (P, T) already computed), and extrapolated simulations are appended into the existing SIM tables with **banded experiment ids** (offset past the original run's experiments) so nothing is overwritten. In the `kmoui` dashboard these appear from the unified SIM database and are labelled `Extrapolated (band b) — <experiment metadata>`.

The content of these databases is accessible from the **Databases** tab of the analysis GUI (`kmoui`): select one of the `.db` files in the run folder, pick a table to display it as a dataframe, and use the copy button to copy the table to the clipboard (tab separated) for pasting into a spreadsheet such as Excel.
